## المبدأ الحاكم

**لا Prototype ولا MVP مبسَّط.** البنية والوظائف الأساسية أوّلًا، والشكل بعدها.
وكل ما يُعلَن «مبنيًّا» هنا مُختبَرٌ فعلًا — لا مكتوبًا فحسب.

## المرحلة ٢ — لوحة الإدارة

### ما أُنجز

| البند | |
|---|---|
| **قائمة الطلبات** | ترشيح بمجموعاتٍ تشغيلية، وبحثٌ بالرقم أو الباركود |
| **تفصيل الطلب** | البنود والمبالغ والسجلّ، ونقلُ الحالة بأزرارٍ تُقرأ من القاعدة |
| **الموظّفون** | إسناد الأدوار وسحبها — بالبحث عن حسابٍ قائم لا بإنشائه |
| أساس Flutter بأربع نكهات | `AppFlavor` + أربعة مداخل، والنكهة تُثبَّت وقت البناء |
| الاتصال بـSupabase | `Db` + مترجم أخطاء عربيّ |
| الجلسة والأدوار | `SessionService` — ينادي `ensure_profile` ويقرأ الأدوار والفروع |
| شاشة الدخول | جوال (OTP) + بريد، والأوّل ينتظر تفعيل المزوّد |
| هيكل اللوحة | شريط جانبيّ على العريض، سفليّ على الضيّق، ومبدّل فروع |
| **لوحة اليوم** | طلبات اليوم، الإيراد، متوسّط الطلب، المتأخّر، وأين كلّ طلب |
| **الخدمات والأسعار** | إضافة وتعديل وإيقاف — الوعد الأساسيّ للنظام |
| **رسوم التوصيل** | الاستراتيجية والرسوم والشرائح، **ومعاينة حيّة** |

### ما بقي في هذه المرحلة

- [ ] **مناطق التوصيل (Geofencing)** — رسم المضلّعات على خريطة
- [ ] **الكوبونات** — إنشاء وحدود واستخدامات
- [ ] **ساعات العمل والطاقة** — تعديل `branch_hours` و`booking_settings`
- [ ] **التقارير والتصدير** — PDF وExcel (نمط `admin_reports_export` في zadgo2)
- [ ] **قوالب الإشعارات** — تحرير النصوص لكل حالة
- [ ] **خريطة السائقين** — الحالة والموقع لحظيًّا

## المصادر المنقول عنها

| المستودع | ما يُنقل منه | ملاحظة |
|---|---|---|
| **`zadgo2`** | الأساس: ٤٩ ألف سطر، أربع شاشات أدوار، باركود، Moyasar، خرائط، تقارير | **لا يُكتب فيه حرف** |
| `zol` | نمط `AppRole` والنكهات، وMoyasar | مرجع |
| `taxi-taiba` | قواعد الأمان، واستعلام الجيوهاش | مرجع؛ **لا تطبيق سائق فيه** |
| `zadam` | Next.js + Supabase + RLS | مرجع للوحة ويب |

**تنبيه على المرحلة ٤**: الخطة كانت الاعتماد على «تاكسي طيبة» موصِّلًا. لكنه
**تطبيق راكب ولا تطبيق سائق فيه** — وثائقه تقولها: «ولا شاشة تسجيل للسائق
بعد». فطرف السائق يُبنى، ونظيره في `zadgo2` (`driver_home`،
`scan_pickup_screen`، `pickup_docket_screen`).

## معايير القبول — ما يُرفض به العمل

قبل أن تُعلَن أي مرحلة «منتهية»:

1. **لا سعر ولا رسم ولا قاعدة عمل في الشيفرة.** كلّها صفوفٌ تعدّلها الإدارة.
2. **لا بيانات وهمية بديلًا عن وظيفة.** شاشة «قيد التجهيز» أصدق من شاشةٍ
   تبدو عاملةً ببيانات ملفَّقة.
3. **الحراسة في القاعدة لا في الشاشة.** كل قيدٍ يجب أن يصمد أمام حزمةٍ معدَّلة.
4. **لا شيفرة تُسلَّم بلا تشغيل.** `flutter analyze` نظيف، والبناء ينجح،
   والشاشة تُفتح فعلًا وتُصوَّر.
5. **رسالة خطأٍ لكل مسار فشل.** بالعربية، ومفهومة، ولا تُفشي بنية.
